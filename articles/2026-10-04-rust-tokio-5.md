## TL;DR

- Tokio の非同期ランタイムは **スケジューラ・リアクター・タスク** の 3 層構造で動く
- `async/await` は糖衣構文であり、コンパイル時に **ステートマシン** へ変換される
- `spawn` / `spawn_blocking` / `block_on` の使い分けを誤ると**スレッド枯渇やデッドロック**を招く
- `select!` マクロの Cancel Safety を理解しないと**データロスト**の原因になる
- `Pin<&mut T>` が必要になる理由は「**自己参照構造体の移動禁止**」にある

---

## 1. なぜ今、Tokio の内部構造を学ぶのか

Tokio はすでに「使えば動く」フェーズを超え、**商用サービスの基盤**として広く採用されています。しかし「`await` を付けたら非同期になる」程度の理解のまま本番コードを書くと、次のようなトラブルに直面します。

- `block_on` をワーカースレッド内で呼んでしまい、スレッドが飢餓状態に
- `select!` の中に `&mut Vec` への書き込みを置いて、キャンセル時にデータが中途半端になる
- CPU バウンドの処理を `async fn` に包んで、ランタイム全体を止めてしまう

これらはすべて「ランタイムがどう動くか」を知っていれば防げるバグです。  
本記事では Tokio v1.x (2024–2025 時点の stable) を対象に、5 つのコアコンセプトを順番に解説します。

## 2. コンセプト 1: `Future` はポーリングモデルで動く

### 2-1. `Future` トレイトの本質

Rust の非同期処理は、次の 1 つのトレイトで成り立っています。

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

重要なのは **「Future は自分からは動かない」** という点です。ランタイムが `poll` を呼んで初めて処理が進みます。  
`Poll` は `Ready(value)` か `Pending` の 2 値を返します。

- `Ready(value)` → 処理完了。値を呼び出し元に返す
- `Pending` → まだ待ち中。ランタイムへ「あとで再度 poll して」と伝える

### 2-2. ポーリングモデルの利点

コールバックモデル (Node.js の旧来型) と比べて、ポーリングモデルには次の利点があります。

| 比較軸 | コールバック | ポーリング (Rust) |
|---|---|---|
| キャンセル | 難しい (コールバック追跡が必要) | `Future` を drop するだけ |
| バックプレッシャー | 手動実装 | `Pending` を返せばよい |
| ゼロコスト | ランタイムオーバーヘッドあり | コンパイル時にステートマシン化 |

### 2-3. Waker の役割

`Pending` を返した `Future` は、再び `poll` されるまで何もしません。  
`Context` に入っている `Waker` を使って「**準備できたよ**」とランタイムに通知します。

```rust
// I/O イベントが来たとき (OS / epoll 側)
waker.wake(); // → ランタイムのキューに再スケジュール
```

この仕組みが、スレッドをブロックせずに数万コネクションを扱える理由です。

## 3. コンセプト 2: ステートマシン変換と `Pin` の必然性

### 3-1. `async fn` はコンパイル時に消える

次の関数を例にとります。

```rust
async fn fetch_then_process(url: &str) -> String {
    let body = http_get(url).await;       // (A) ここで Pending になりうる
    let processed = cpu_process(&body);   // (B)
    processed
}
```

コンパイラはこれを、おおよそ次のようなステートマシンに変換します。

```rust
enum FetchThenProcess<'a> {
    // await (A) を待っている状態
    WaitingHttp {
        url: &'a str,
        fut: HttpGetFuture,
    },
    // (A) が終わり (B) を処理している状態
    Processing {
        body: String, // <-- (A) の結果を保持
    },
    Done,
}
```

`await` の数だけステートが増え、**各ステートには「次の await まで必要な変数」が格納**されます。

### 3-2. なぜ `Pin` が必要か

問題はここです。`WaitingHttp` ステートで `body` を参照する場合を考えます。

```rust
async fn example() {
    let s = String::from("hello");
    let reference = &s; // s への参照
    some_async_fn().await;
    println!("{}", reference); // await をまたいで参照を使う
}
```

ステートマシン内には `s` と `reference` が **同じ構造体フィールドとして** 共存します。  
この構造体をメモリ上で移動すると、`reference` が古いアドレスを指したままになり **ダングリングポインタ** になります。

`Pin<&mut T>` は「**この値をヒープ上の同じアドレスに固定する**」ことを型レベルで保証します。

```
移動前:  [  s (addr=0x100)  | ref=0x100  ]
移動後:  [  s (addr=0x200)  | ref=0x100  ] ← 壊れる
                              ^^^^^^^^^^^^
                              Pin があれば移動できないのでこの状況が起きない
```

`Unpin` トレイトは「移動しても安全」を示すマーカーです。プリミティブ型はほぼ `Unpin` を実装しています。

## 4. コンセプト 3: Tokio のスレッドプールとスケジューラ

### 4-1. ワークスティーリングスケジューラ

Tokio のデフォルトランタイムは **マルチスレッド + ワークスティーリング** です。

```
Worker 0: [Task A] [Task B]
Worker 1: [Task C]
Worker 2: []          ← アイドル → Worker 0 からタスクを盗む
Worker 3: [Task D] [Task E] [Task F]
```

各ワーカースレッドはローカルキューを持ち、空になったら他スレッドのキューから「スティール」します。  
これにより CPU 利用率が均等化され、特定スレッドへの偏りを防ぎます。

### 4-2. `spawn` vs `spawn_blocking` vs `block_on`

これを正しく使い分けることが、Tokio 運用の最重要ポイントです。

#### `tokio::spawn`

```rust
let handle = tokio::spawn(async {
    // 非同期タスクをワーカープールに投入
    do_async_work().await
});
let result = handle.await?;
```

- I/O バウンドの処理に使う
- ワーカースレッドを**ブロックしない**ことが前提

#### `tokio::task::spawn_blocking`

```rust
let result = tokio::task::spawn_blocking(|| {
    // 同期・CPU バウンドの処理
    heavy_compute()
}).await?;
```

- **専用のブロッキングスレッドプール**で実行される (デフォルト最大 512 スレッド)
- 長時間の同期 I/O・CPU 負荷処理はここへ
- 絶対にワーカースレッド上で同期 I/O を呼んではいけない

#### `block_on` (アンチパターン例)

```rust
// ❌ ワーカースレッド内で block_on を呼ぶ → デッドロック
tokio::spawn(async {
    let result = tokio::runtime::Handle::current()
        .block_on(some_future()); // 同スレッドをブロック → 他タスクが進めない
});
```

`block_on` は「非同期でないコンテキスト (例: `main` 関数・テスト) から非同期処理を起動する」用途限定です。

### 4-3. スレッド数のチューニング

```rust
let rt = tokio::runtime::Builder::new_multi_thread()
    .worker_threads(4)          // デフォルト: 論理 CPU 数
    .max_blocking_threads(128)  // デフォルト: 512
    .thread_name("my-worker")
    .build()
    .unwrap();
```

CPU バウンドワークロードなら `worker_threads = 論理 CPU 数` が最適です。  
I/O バウンドなら CPU 数より多くしても意味はほぼなく、むしろコンテキストスイッチが増えます。

## 5. コンセプト 4: リアクターと I/O ドライバ

### 5-1. epoll / kqueue / IOCP の抽象化

Tokio の I/O ドライバは **`mio`** クレートを通じて OS の I/O 多重化機能を使います。

| OS | 機構 |
|---|---|
| Linux | `epoll` |
| macOS / BSD | `kqueue` |
| Windows | `IOCP` |

### 5-2. TcpStream の裏側

```rust
let mut stream = tokio::net::TcpStream::connect("127.0.0.1:8080").await?;
stream.write_all(b"GET / HTTP/1.1\r\n\r\n").await?;
```

1. `connect` が呼ばれると、ノンブロッキングソケットを作成して epoll に登録
2. `await` で `Pending` を返し、スレッドを解放
3. カーネルが「接続完了」イベントを検知 → mio が Waker を呼び出す
4. Tokio スケジューラがタスクを再キューイング → `poll` が再呼び出しされる

この流れにより、**1 スレッドで数万の TCP コネクション**を同時に扱えます。

### 5-3. シングルスレッドランタイム (`current_thread`)

WebAssembly やリソース制約環境では、マルチスレッドが使えません。

```rust
let rt = tokio::runtime::Builder::new_current_thread()
    .enable_all()
    .build()?;
```

すべてのタスクが 1 スレッドで協調実行されます。`Send` 制約が不要になるため、`Rc` や生ポインタを含む型も `spawn` できます (`spawn_local` を使用)。

## 6. コンセプト 5: `select!` マクロと Cancel Safety

### 6-1. `select!` の基本

```rust
tokio::select! {
    result = tcp_read(&mut socket) => {
        println!("read: {:?}", result);
    }
    _ = tokio::time::sleep(Duration::from_secs(5)) => {
        println!("timeout");
    }
}
```

複数の `Future` を同時に poll し、**最初に `Ready` になったブランチだけ実行**します。  
残りの `Future` は **drop (=キャンセル)** されます。

### 6-2. Cancel Safety とは

問題が起きるのは「キャンセルされたとき、副作用が中途半端に適用されていた場合」です。

```rust
// ❌ Cancel Unsafe な例
async fn append_to_vec(buf: &mut Vec<u8>, stream: &mut TcpStream) {
    let mut tmp = [0u8; 1024];
    let n = stream.read(&mut tmp).await; // ← ここでキャンセルされると...
    buf.extend_from_slice(&tmp[..n]);    // ← この行は実行されない → buf は不完全
}

// select! 内で使うと:
tokio::select! {
    _ = append_to_vec(&mut buf, &mut stream) => {}
    _ = cancel_signal() => {}  // キャンセルされたら buf が壊れる
}
```

Tokio ドキュメントでは各非同期メソッドに **"Cancel safe"** かどうかを明記しています。

| メソッド | Cancel Safe? |
|---|---|
| `TcpStream::read` | ✅ Yes (バッファへの書き込み前にキャンセル) |
| `AsyncReadExt::read_exact` | ❌ No (部分読み込みが起きうる) |
| `Mutex::lock` | ✅ Yes (ロック取得前ならキャンセル安全) |
| `oneshot::recv` | ✅ Yes |
| `mpsc::Receiver::recv` | ✅ Yes |

### 6-3. Cancel Safe な設計パターン

**パターン 1: `tokio::sync::watch` で最終値のみ保持**

```rust
let (tx, mut rx) = tokio::sync::watch::channel(State::default());

tokio::select! {
    _ = rx.changed() => {
        let state = rx.borrow().clone(); // キャンセルされても watch は整合性を保つ
    }
    _ = cancel_signal() => {}
}
```

**パターン 2: 処理を完結単位に分割してから `select!` に渡す**

```rust
// ✅ 読み込みと処理を分離
let data = stream.read_buf(&mut buf).await?; // まず完全に読む
tokio::select! {
    _ = process(buf.as_ref()) => {} // 処理フェーズは冪等に設計
    _ = cancel_signal() => {}
}
```

## 7. 実践: 5 つのコンセプトを組み合わせたエコーサーバ

以上を踏まえた、堅牢なエコーサーバの最小実装例です。

```rust
use tokio::{
    io::{AsyncBufReadExt, AsyncWriteExt, BufReader},
    net::TcpListener,
    sync::CancellationToken,
};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let listener = TcpListener::bind("0.0.0.0:8080").await?;
    let token = CancellationToken::new();
    let shutdown = token.clone();

    // Ctrl+C でグレースフルシャットダウン
    tokio::spawn(async move {
        tokio::signal::ctrl_c().await.unwrap();
        shutdown.cancel();
    });

    loop {
        tokio::select! {
            Ok((socket, addr)) = listener.accept() => {
                let child_token = token.child_token();
                tokio::spawn(async move {
                    if let Err(e) = handle_conn(socket, child_token).await {
                        eprintln!("[{addr}] error: {e}");
                    }
                });
            }
            _ = token.cancelled() => {
                println!("shutdown signal received");
                break;
            }
        }
    }
    Ok(())
}

async fn handle_conn(
    socket: tokio::net::TcpStream,
    token: CancellationToken,
) -> anyhow::Result<()> {
    let (reader, mut writer) = socket.into_split();
    let mut lines = BufReader::new(reader).lines();

    loop {
        tokio::select! {
            // Cancel safe: BufReader::next_line は Cancel safe
            result = lines.next_line() => {
                match result? {
                    Some(line) => {
                        writer.write_all(line.as_bytes()).await?;
                        writer.write_all(b"\n").await?;
                    }
                    None => break, // EOF
                }
            }
            _ = token.cancelled() => {
                writer.write_all(b"Server shutting down\n").await.ok();
                break;
            }
        }
    }
    Ok(())
}
```

**注目ポイント:**

- `CancellationToken` でグレースフルシャットダウンを型安全に実現 (Tokio 1.x 推奨パターン)
- `select!` には Cancel Safe な `BufReader::next_line` のみを使用
- コネクション処理を `spawn` で独立タスク化し、accept ループをブロックしない

## 8. よくあるハマりパターン まとめ

| ハマりパターン | 原因 | 解決策 |
|---|---|---|
| タスクが進まない / 詰まる | ワーカースレッドを `std::thread::sleep` でブロック | `tokio::time::sleep` を使う |
| CPU バウンド処理でレスポンスが遅くなる | `async fn` に重い計算を置いた | `spawn_blocking` に移す |
| `select!` 後にデータが欠損する | Cancel Unsafe なメソッドを `select!` に渡した | Tokio docs の "Cancel safe" 表記を確認 |
| ランタイム内で `block_on` を呼んでデッドロック | ワーカースレッド上で `block_on` | `spawn_blocking` か設計を見直す |
| `Pin` コンパイルエラーが解決できない | 自己参照構造体を手実装 | `async fn` + `tokio::pin!()` マクロを使う |

## 9. まとめ

Tokio の非同期ランタイムを理解するためのキーポイントを再確認します。

1. **`Future` はポーリングモデル** — `poll` が呼ばれるまで何もしない。`Waker` で再起動を通知
2. **`async fn` はステートマシン** — `await` ごとにステートが切り替わる。`Pin` は自己参照の移動を防ぐ
3. **スレッドプールを正しく使い分ける** — `spawn` は非同期 I/O 用、`spawn_blocking` は同期・CPU バウンド用
4. **リアクターが epoll/kqueue を抽象化** — 1 スレッドで数万の I/O を多重化できる基盤
5. **`select!` の Cancel Safety を確認** — キャンセル時の副作用を設計段階で考慮する

これらを体系的に把握することで、「なんとなく動く Tokio コード」から「**障害に強く、パフォーマンスを意図的にコントロールできる Tokio コード**」へ移行できます。
