## TL;DR

- Claude Code は「指示して待つ」ではなく「協調しながら育てる」ツール
- CLAUDE.md・サブエージェント・コスト制御の 3 軸を押さえると生産性が跳ね上がる
- 失敗パターンを知ることで、無駄なトークン消費と手戻りを大幅に減らせる

---

## はじめに

2025 年後半、Claude Code は「試したことある」から「毎日使う」フェーズへと移行しつつある。しかし単純に「タスクを投げて待つ」だけでは、期待した結果が返ってこないことも多い。

本記事では、実際に数週間かけて試行錯誤した中で見えてきた **「機能する使い方」** と **「ハマりやすい落とし穴」** を 7 つのパターンとして整理する。コードの品質や開発速度に悩んでいるエンジニアにとって、すぐに使えるヒントが見つかるはずだ。

---

## 前提: Claude Code とは何か

Claude Code は Anthropic が提供する CLI ベースのコーディングエージェントだ。ターミナルから起動し、ファイルの読み書き・シェルコマンドの実行・Git 操作を自律的に行いながらタスクを完遂する。

```bash
# 基本的な起動
claude

# 特定タスクをワンショット実行 (対話なし)
claude -p "src/utils/date.ts に ISO 8601 フォーマット関数を追加して"
```

中核の設計思想は **「人間とエージェントの協調」** だ。単なる補完ツールではなく、プロジェクト全体のコンテキストを保持しながら複数ファイルにまたがる変更を行える。

---

## パターン 1: CLAUDE.md でコンテキストを制御する

### 問題

何も設定しなければ、Claude Code はプロジェクトのコーディング規約・ディレクトリ構成・禁止操作を知らない状態で動く。「なぜか ESLint ルールを無視したコードが生成される」「本番環境に影響するファイルをいじってくる」といった事象が起きる。

### 解決策: CLAUDE.md を書く

プロジェクトルートに `CLAUDE.md` を配置すると、Claude Code は毎回このファイルを読み込んだ状態で動作する。

```markdown
# CLAUDE.md

## プロジェクト概要
Next.js 14 (App Router) + TypeScript + Prisma のフルスタックアプリ

## ディレクトリ構成
- src/app/         : App Router のページ・レイアウト
- src/components/  : 再利用可能な UI コンポーネント
- src/lib/         : ユーティリティ・DB クライアント
- prisma/          : スキーマ・マイグレーション

## 命名規則
- コンポーネント: PascalCase (例: UserCard.tsx)
- ユーティリティ: camelCase (例: formatDate.ts)
- 定数: SCREAMING_SNAKE_CASE

## 禁止事項
- prisma/migrations/ は直接編集しない
- .env ファイルへの書き込みは行わない
- any 型の使用は原則禁止 (型引数で解決すること)

## テスト
- ユニットテスト: Vitest
- E2E: Playwright
- PR 前に `pnpm test` がグリーンであること
```

**ポイント**: 「禁止事項」を明示するだけで、予期しない操作をほぼ防げる。ファイル数が増えるほど ROI が高い。

## パターン 2: タスクを「スコープ」で区切って渡す

### 問題

「このアプリの認証機能をリファクタして」のような大きな指示は、Claude Code が誤った方向に走り続けたとき気づくのが遅れる。また途中で方針転換すると、それまでの変更が無駄になる。

### 解決策: 1 PR = 1 タスク原則

```
# 悪い例
「ユーザー管理画面を全部作って」

# 良い例 (スコープを分割)
「UserList コンポーネントを src/components/users/UserList.tsx に新規作成して。
 props は users: User[] だけ。テーブル形式で name / email / createdAt を表示する。
 スタイルは Tailwind を使い、空配列のとき "ユーザーが存在しません" と表示する。」
```

**なぜ効くのか**: Claude Code はタスクが小さいほど「完了基準」を自分で判断しやすい。大きなタスクは内部で暗黙的に分解されるが、その分解が意図と一致しないことが多い。

---

## パターン 3: ツール許可をタスクに合わせて絞る

Claude Code は実行時にツール (ファイル読み書き・シェル実行・ブラウザ等) の使用可否を制御できる。

```bash
# ファイル書き込みのみ許可・シェル実行は禁止
claude --allowedTools "Read,Write,Edit"

# 読み取り専用 (コードレビューや調査タスクに最適)
claude --allowedTools "Read"
```

「シェル実行を許可しなければ `rm -rf` は物理的に実行できない」という安心感は、チーム導入時の心理的ハードルを下げる効果がある。

CI 環境で非対話的に実行するときは `--dangerously-skip-permissions` フラグが使えるが、**ローカル開発での常用は推奨しない**。権限の明示的な管理こそが事故を防ぐ。

## パターン 4: 長い会話は要約してリセットする

### 問題

Claude Code はコンテキストウィンドウが長くなるほど、初期の指示を「薄く」扱う傾向がある。「最初に言ったコーディング規約をいつの間にか守らなくなった」という現象はこれが原因だ。

### 解決策: `/compact` コマンドを使う

```
/compact
```

このコマンドは会話履歴を圧縮し、重要な決定事項・現在の状態・未完了タスクのみを残す。コンテキストを圧迫していた長大なファイル内容やデバッグログが削除され、モデルが「今何をすべきか」に集中できる状態になる。

**目安**: 会話が 30 往復を超えたら `/compact` を検討する。特に大きなファイルを複数読み込んだ後は積極的に使う。

## パターン 5: サブエージェントで並列処理する

Claude Code 0.2 以降、`Task` ツールを使ってサブエージェントを起動できる。これにより独立したタスクを並列実行できる。

```
# 親エージェントへの指示例
「以下を並列で行ってください:
 1. src/components/Header.tsx のアクセシビリティ改善 (aria 属性の追加)
 2. src/components/Footer.tsx のアクセシビリティ改善 (aria 属性の追加)
 3. src/utils/format.ts にユニットテストを追加」
```

**使いどころ**:
- 同じ種類の作業が複数ファイルに存在するとき
- 互いに依存しない機能追加
- テスト追加とドキュメント更新を同時に行うとき

**注意点**: 同一ファイルを複数サブエージェントが編集すると競合が起きる。ファイル単位で重複がないようにタスクを切る。

## パターン 6: コスト意識を持つ ─ :free モデルの使い所

Claude Code 自体は Anthropic API を消費するが、タスクの性質によってモデルを使い分けることでコストを大幅に下げられる。

| タスク種別 | 推奨モデル層 | 理由 |
|---|---|---|
| 定型コード生成・テスト追加 | 軽量モデル | 正確性より速度・コストが重要 |
| 設計判断・アーキテクチャ検討 | 高性能モデル | 深い推論が必要 |
| ドキュメント生成・コメント追加 | 軽量モデル | 定型作業 |
| 複雑なバグ調査・根本原因分析 | 高性能モデル | 推論の深さが直接品質に影響 |

OpenRouter の `:free` エンドポイント (`qwen/qwen3-235b-a22b:free`, `google/gemini-2.0-flash-exp:free` 等) は、自動化スクリプトや繰り返しタスクに組み込む用途で特に有効だ。

```typescript
// OpenRouter :free モデルを使った簡易呼び出し例
const response = await fetch('https://openrouter.ai/api/v1/chat/completions', {
  method: 'POST',
  headers: {
    'Authorization': `Bearer ${process.env.OPENROUTER_API_KEY}`,
    'Content-Type': 'application/json',
  },
  body: JSON.stringify({
    model: 'qwen/qwen3-235b-a22b:free',
    messages: [{ role: 'user', content: prompt }],
  }),
});
```

**ポイント**: `:free` モデルはレートリミットがあるため、バースト処理より定常的なバックグラウンドタスクに向く。

## パターン 7: Git を「セーフティネット」として活用する

Claude Code は変更を加える前に自動的にバックアップを作成する機能を持たない。**Git コミットが唯一の安全網だ。**

### 推奨フロー

```bash
# 1. Claude Code に渡す前に必ずコミットまたはスタッシュ
git add -A && git commit -m "wip: before claude code refactor"

# 2. Claude Code にタスクを渡す

# 3. 結果を確認
git diff

# 4. 意図と一致していれば追加コミット
git add -A && git commit -m "refactor: extract UserCard component"

# 5. 意図と違えばリセット
git checkout .
```

**さらに踏み込む**: ブランチ戦略と組み合わせると安全性が増す。

```bash
# 実験的なタスクは専用ブランチで
git checkout -b claude/refactor-user-module
# (Claude Code にタスクを渡す)
# 気に入らなければブランチごと削除
git checkout main && git branch -D claude/refactor-user-module
```

## よくあるハマりパターンと対処法

| ハマりパターン | 原因 | 対処法 |
|---|---|---|
| 存在しない関数を呼び出すコードが生成された | コンテキスト不足 | CLAUDE.md に型定義ファイルのパスを明示する |
| テストが通っていないのにタスク完了と報告される | 完了基準が曖昧 | 「`pnpm test` がグリーンになること」を完了基準として明記 |
| 同じバグを 3 回直して 3 回とも失敗した | 根本原因の分析不足 | 「なぜこのバグが起きているか仮説を 3 つ列挙してから修正して」と指示 |
| リファクタ後にパフォーマンスが悪化した | 非機能要件の伝達不足 | CLAUDE.md または指示文に「N+1 クエリを避ける」等の制約を追加 |

## まとめ

Claude Code を使いこなすためのポイントを再整理する。

1. **CLAUDE.md で禁止事項を明示** ─ 意図しない操作を防ぐ最も確実な方法
2. **タスクを小さく区切る** ─ 完了基準が明確になり手戻りが減る
3. **ツール許可を絞る** ─ 安全性と信頼感が上がり、チーム展開しやすくなる
4. **`/compact` でコンテキストをリセット** ─ 長い作業では定期的に実行する
5. **サブエージェントで並列化** ─ 独立タスクは迷わず並列に渡す
6. **モデルを使い分けてコストを下げる** ─ 重さに見合う仕事を割り当てる
7. **Git を頻繁にコミット** ─ Claude Code の唯一のセーフティネット

Claude Code は「魔法のように全部やってくれるツール」ではなく、「的確に指示すれば強力なパートナーになるツール」だ。この 7 つのパターンを土台に、自分のプロジェクトに合ったワークフローを育てていってほしい。
