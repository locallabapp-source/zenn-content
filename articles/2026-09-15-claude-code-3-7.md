## TL;DR

- Claude Code は「何を頼むか」より「**どう頼むか**」で成果物の質が大きく変わる
- 曖昧な指示は曖昧なコードを生む。構造化された指示は構造化されたコードを生む
- この記事では実務で効果を確認した 7 つのパターンを、失敗例と比較しながら解説する

---

## はじめに

Claude Code が登場してから、エンジニアの開発スタイルは確実に変わりつつある。しかし多くの人が「うまく使えている気がしない」と感じる理由は、モデルの限界ではなく **プロンプトの設計** にある。

ターミナルで動く Claude Code は、チャット UI とは異なる独自の強みを持つ。ファイルシステムへのアクセス、コマンド実行、差分確認、リファクタリングのフィードバックループ。これらを活かすためのプロンプトパターンを、**7 つに整理**した。

---

## パターン 1: 「目的 → 制約 → 成功条件」の三段構成

### ❌ 失敗例

```
認証機能を実装してください
```

このプロンプトは Claude に大量の推測をさせる。JWT か Session か? DB は? エラーハンドリングのスタイルは?

### ✅ 改善例

```
【目的】
Next.js App Router で JWT ベースのログイン機能を実装してほしい。

【制約】
- DB は既存の PostgreSQL (Drizzle ORM 使用)
- トークンは httpOnly Cookie に格納する
- refresh token は不要 (有効期限 24h)
- Edge Runtime は使わない

【成功条件】
- /api/auth/login が POST を受け取り、200 or 401 を返す
- middleware.ts で未認証ユーザーを /login にリダイレクトする
- 既存の src/lib/db.ts と型定義を壊さない
```

三段構成にするだけで、Claude の推測コストがほぼゼロになり、**最初のレスポンスから使えるコード**が返ってくる確率が劇的に上がる。

---

## パターン 2: 既存コードへの「参照点」を明示する

Claude Code はファイルシステムを読める。この強みを活かすには、**どのファイルを参照すべきか**を明示するのが鍵だ。

### ❌ 失敗例

```
既存のスタイルに合わせてコンポーネントを作って
```

### ✅ 改善例

```
src/components/ui/Button.tsx のスタイル・型定義・命名規則を参照して、
同じパターンで Input コンポーネントを作って。

特に以下を踏襲してほしい:
- variant props の定義方法
- cn() ユーティリティの使い方
- forwardRef の書き方
```

参照点を明示することで、プロジェクト固有の慣習が引き継がれ、**レビュー差し戻しが減る**。

---

## パターン 3: 「やること」より「やらないこと」を先に書く

人間のレビュアーが「ここだけ触って」と言うように、Claude にも **スコープの境界** を伝える必要がある。

### ❌ 失敗例

```
パフォーマンスを改善して
```

これは大規模リファクタリングのトリガーになりうる。

### ✅ 改善例

```
以下のファイルのパフォーマンスを改善してほしい。

【スコープ外 (触らないで)】
- APIの呼び出し方 (別チームが管理)
- CSS / スタイル
- テストファイル

【スコープ内】
- src/features/dashboard/DataTable.tsx の再レンダリング削減
- useMemo / useCallback の追加のみ
- React DevTools Profiler で確認した「不要な再レンダリング 14 回」を 3 回以下にしたい
```

境界を明示すると、Claude が余計なファイルを触るリスクが大幅に下がる。

---

## パターン 4: 「思考ステップ」を明示的に分割する

複雑な問題を 1 プロンプトで解こうとすると、Claude も人間も迷子になる。**タスクを段階に分割**してから依頼するパターンが効果的だ。

### 実装例

```
以下の 3 ステップで進めてほしい。各ステップ完了後に確認を求めること。

ステップ 1: 現在の src/hooks/useAuth.ts の問題点を箇条書きで洗い出す (コードは書かない)
ステップ 2: 私の OK を受けてから、改善案を 2 パターン提示する (コードは書かない)
ステップ 3: 私が選んだパターンを実装する

まずステップ 1 から始めて。
```

**「コードは書かない」** という制約が重要で、これがないと Claude は即座に実装に走ってしまう。分析→設計→実装の分離がレビュー品質を上げる。

---

## パターン 5: エラーメッセージは「全文コピー + 再現コンテキスト」で渡す

### ❌ 失敗例

```
型エラーが出て困ってます
```

### ✅ 改善例

````
以下の型エラーを修正してほしい。

【エラー全文】
```
Type '{ userId: string; role: "admin" | "user"; }' is not assignable to type 'Session'.
  Types of property 'role' are incompatible.
    Type '"admin" | "user"' is not assignable to type '"admin" | "editor" | "viewer"'.
```

【発生場所】
src/lib/auth/session.ts の 42 行目、createSession() 関数

【直前に行った変更】
types/auth.ts の Role 型に "editor" と "viewer" を追加した (PR #142)

【直したい方向性】
session.ts 側の型を更新したい。types/auth.ts は変えないで。
````

エラーの「全文」「場所」「直前の変更」「方向性」の 4 点セットが揃うと、Claude の診断精度が上がる。

## パターン 6: テスト駆動プロンプト (TDP)

実装前に **テストケースを列挙**させてから実装させるパターン。Red-Green サイクルを Claude と一緒に回す。

```
以下の関数を実装する前に、まずテストケースを洗い出して。

関数: formatPrice(amount: number, currency: string): string

テストケースとして考慮してほしいこと:
- 通貨コードの種類 (JPY, USD, EUR, ...)
- 小数点の扱い (JPY は整数, USD は 2 桁)
- 0 円・負の値
- 非常に大きな数値 (1,000,000 以上)
- currency が不正な文字列の場合

Vitest 形式でテストコードだけ先に書いて。実装はまだ書かないで。
```

テストが確定したら `実装して` とだけ打てばよい。このパターンは**仕様の認識ズレ**を実装前に発見できる利点がある。

---

## パターン 7: 「なぜこう書いたか」の説明要求

Claude が書いたコードをそのままマージするのは危険だ。**意図の説明**を求めるプロンプトを習慣化すると、レビューコストが下がり、自分の理解も深まる。

```
実装してくれたコードについて、以下の点を説明して:

1. useCallback の依存配列に exhaustive-deps があえて含まれていないが、その理由
2. AbortController を使ったのはなぜか。useEffect の cleanup で return だけでは不足?
3. このアプローチの代替案と、今回の選択の trade-off

コードは変更せず、説明だけでOK。
```

「なぜ」を聞く習慣は、**Claude の判断ミスを発見するセーフネット**にもなる。モデルが自信を持って間違えるケースは存在するため、このパターンは特に重要だ。

---

## 7 パターンの比較表

| パターン | 主なメリット | 特に効く場面 |
|---|---|---|
| 1. 三段構成 | 推測コスト削減・初回成功率向上 | 新機能実装 |
| 2. 参照点の明示 | スタイル統一・レビュー削減 | コンポーネント追加 |
| 3. スコープ境界 | 意図しない変更防止 | リファクタリング・改善 |
| 4. ステップ分割 | 分析と実装の分離・確認機会確保 | 複雑な設計変更 |
| 5. エラー 4 点セット | 診断精度向上・無関係な修正防止 | デバッグ |
| 6. テスト駆動 | 仕様ズレの早期発見 | ロジック実装 |
| 7. 説明要求 | 理解促進・ミス発見 | レビュー・学習 |

---

## まとめ

Claude Code の真価は「コードを書かせる」ことではなく、**自分の思考を構造化して高速にフィードバックを得るループを回すこと**にある。

7 つのパターンに共通しているのは「**Claude に推測させる余地を減らす**」という設計思想だ。曖昧な余白はモデルが埋めるのではなく、自分の意図で埋める。その習慣が、AI との協働品質を底上げする。

明日から 1 つだけ試すとしたら、**パターン 1 の三段構成**から始めてみてほしい。最初のレスポンスが変わるのを体感できるはずだ。
