## TL;DR

- Claude Code はターミナルから直接呼び出せる AI コーディングアシスタントで、CI/CD パイプラインへの統合も容易
- プロンプト設計次第でレビュー精度が大きく変わる——5 つのパターンを実例付きで紹介
- `--no-tools` フラグや `--system-prompt` オプションを活用することでセキュリティと再現性を両立できる

---

## 背景：コードレビューのボトルネック

Pull Request のレビューは、エンジニアリングチームにとって最もコストのかかる非同期コミュニケーションの一つだ。

- レビュアーが手動で確認する項目は多岐にわたる（型安全性・テストカバレッジ・セキュリティ・パフォーマンス）
- 「LGTM 文化」が蔓延すると、機械的にチェックできるはずのバグが本番に流出する
- 深夜マージ・大型 PR によるレビュー疲弊は普遍的な課題

Claude Code（Anthropic 公式 CLI）を使えば、これらのチェックを **プロンプトテンプレート化** して自動化できる。本記事では実践的なプロンプトパターンを 5 つ紹介する。


## パターン 1：型安全性チェック（TypeScript 向け）

TypeScript プロジェクトで `any` の乱用や `as` キャストの危険性を機械的に洗い出す。

### プロンプト

```text
あなたは TypeScript のコードレビュアーです。
以下のコードを読み、下記の観点だけを検査してください。

【検査観点】
1. `any` 型の使用箇所とその代替案
2. 型アサーション (`as`) の危険な使用
3. `unknown` を使うべき箇所で `any` を使っているケース
4. Zod / Valibot 等のランタイムバリデーションが欠落している外部入力

【出力フォーマット】
- 行番号: 問題の概要 → 推奨修正

問題がなければ "✅ 型安全性: 問題なし" とだけ出力してください。

--- コード ---
{CODE}
```

### 使い方

```bash
# git diff をそのまま流し込む
git diff origin/main...HEAD -- '*.ts' | claude --no-markdown \
  --system "あなたは TypeScript コードレビュアーです。指示通りの形式でのみ回答してください。" \
  "$(cat prompts/type-safety-review.txt)"
```

### 出力例

```
12行目: `data as UserResponse` — APIレスポンスの型アサション
  → zod の `UserResponseSchema.parse(data)` でランタイム検証を推奨

47行目: 引数 `callback: any` → `callback: (err: Error | null, result: T) => void` に変更可能
```

## パターン 2：セキュリティ脆弱性スキャン（OWASP Top 10 準拠）

ビジネスロジックの脆弱性は静的解析ツールが見落としがちだ。LLM はコンテキストを理解した上でロジックバグを指摘できる。

### プロンプト

```text
セキュリティ審査官として、以下のコードを OWASP Top 10 (2021) の観点から審査してください。

特に注目してほしい項目:
- A01: アクセス制御の不備（認可ロジックのバイパス可能性）
- A02: 暗号化の失敗（平文保存・弱いハッシュ関数）
- A03: インジェクション（SQLi, XSS, コマンドインジェクション）
- A07: 認証・セッション管理の不備

リスクレベルを [CRITICAL / HIGH / MEDIUM / LOW / INFO] で付けてください。
コード修正案も添えてください。

--- コード ---
{CODE}
```

### 実際に検出できるパターン例（公開されている典型的な脆弱性）

```typescript
// ❌ 典型的な SQL インジェクション (教科書例)
const query = `SELECT * FROM users WHERE id = ${req.params.id}`;

// ✅ プレースホルダを使う
const query = "SELECT * FROM users WHERE id = ?";
db.execute(query, [req.params.id]);
```

Claude Code にこのようなコードを流すと以下のように検出される:

```
[CRITICAL] 3行目: SQLインジェクション脆弱性
  ユーザー入力 `req.params.id` を文字列テンプレートで直接埋め込んでいます。
  攻撃例: id=1 OR 1=1--
  修正: プリペアドステートメント or ORM のクエリビルダを使用してください。
```

## パターン 3：パフォーマンスレビュー（React コンポーネント向け）

React の再レンダリング問題や N+1 的なデータ取得パターンを検出する。

### プロンプト

```text
React パフォーマンスの専門家として以下のコンポーネントをレビューしてください。

チェック観点:
1. 不要な再レンダリングを引き起こす useMemo / useCallback の欠落
2. 巨大なオブジェクトを Context に入れているケース
3. useEffect の依存配列の誤り（過剰 / 不足）
4. 子コンポーネントへの inline オブジェクト / 関数の渡し方
5. key prop の不適切な使用（index をキーにしているケース）

各問題について:
- 問題のある行
- なぜパフォーマンスに影響するか（1〜2文）
- 修正コード（最小限の変更で）

--- コード ---
{CODE}
```

### 出力例

```
23行目: `<Child config={{ timeout: 500, retry: 3 }} />`
  毎レンダリングで新しいオブジェクトが生成されるため、Child は常に再レンダリングされます。

修正:
  // コンポーネント外 or useMemo で定数化
  const DEFAULT_CONFIG = { timeout: 500, retry: 3 } as const;
  // ...
  <Child config={DEFAULT_CONFIG} />
```

## パターン 4：テストカバレッジ不足の自動指摘 + テストコード生成

「テストを書いてください」だけでは質の低いテストが生成される。制約を与えることが重要。

### プロンプト

```text
以下のコードに対するユニットテストを作成してください。

制約:
- テストフレームワーク: Vitest (describe / it / expect を使う)
- モック: vi.mock() を使い外部依存を必ず分離する
- 各テストケースに日本語のコメントで「何を検証しているか」を書く
- カバーすべき境界値:
  - 正常系 (happy path)
  - null / undefined の入力
  - 空配列・空文字列
  - 最大値・最小値
  - 非同期エラー (reject / throw)

テストコードのみを出力し、説明文は不要です。

--- 対象コード ---
{CODE}
```

### 実行例（bash ワンライナー）

```bash
# src/ 配下の未テストファイルにテストを自動生成
for f in $(git diff origin/main --name-only | grep '\.ts$' | grep -v '\.test\.ts$'); do
  echo "=== $f ===" >> review-output.md
  claude "$(cat prompts/test-gen.txt | sed "s|{CODE}|$(cat $f)|")" >> review-output.md
done
```

## パターン 5：変更影響範囲の説明文自動生成（PR Description 作成）

diff を渡して「何が変わったか」を人間が読める文章に変換する。非エンジニアとの協業・レビュー依頼コストを大幅に削減できる。

### プロンプト

```text
Git の差分を読んで、Pull Request の説明文を生成してください。

出力フォーマット (Markdown):
## 変更概要
1〜3 文で変更の目的を説明

## 変更内容
- 箇条書きで具体的な変更点 (ファイル名 + 変更の意図)

## 影響範囲
- 変更によって影響を受ける機能・画面・API エンドポイント

## テスト方法
- レビュアーが手動確認すべき手順 (あれば)

## 注意事項
- 破壊的変更・マイグレーション・環境変数の追加がある場合のみ記述

以下の diff を解析してください:
--- diff ---
{DIFF}
```

### CI/CD 組み込み例（GitHub Actions 風の疑似コード）

```yaml
# .github/workflows/auto-pr-description.yml の概念
on:
  pull_request:
    types: [opened]

jobs:
  generate-description:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Generate PR description
        run: |
          DIFF=$(git diff origin/main...HEAD)
          PROMPT=$(cat prompts/pr-description.txt | sed "s|{DIFF}|$DIFF|")
          DESCRIPTION=$(claude --no-markdown "$PROMPT")
          gh pr edit ${{ github.event.pull_request.number }} --body "$DESCRIPTION"
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

> **注意**: API キーは必ず CI の Secrets として管理し、コードにハードコードしないこと。

## 5 パターンをまとめた CLI ラッパー

```bash
#!/usr/bin/env bash
# review.sh — Claude Code コードレビューラッパー
# 使い方: ./review.sh <mode> <file>
# mode: type | security | perf | test | pr

set -euo pipefail

MODE="${1:-}"
FILE="${2:-}"
PROMPT_DIR="$(dirname "$0")/prompts"

if [[ -z "$MODE" || -z "$FILE" ]]; then
  echo "Usage: $0 <type|security|perf|test|pr> <file_or_diff>" >&2
  exit 1
fi

case "$MODE" in
  type)     PROMPT_FILE="type-safety-review.txt" ;;
  security) PROMPT_FILE="security-review.txt" ;;
  perf)     PROMPT_FILE="perf-review.txt" ;;
  test)     PROMPT_FILE="test-gen.txt" ;;
  pr)       PROMPT_FILE="pr-description.txt" ;;
  *)
    echo "Unknown mode: $MODE" >&2
    exit 1
    ;;
esac

CODE=$(cat "$FILE")
PROMPT=$(sed "s|{CODE}|$CODE|g" "$PROMPT_DIR/$PROMPT_FILE")

claude --no-markdown "$PROMPT"
```

```bash
# 使用例
./review.sh security src/api/auth.ts
./review.sh type src/models/user.ts
./review.sh pr <(git diff origin/main...HEAD)
```

## 実運用でハマりやすい 3 つの注意点

### 1. トークン上限対策

大きなファイル（1,000 行超）を丸ごと渡すとコンテキストウィンドウを圧迫する。

```bash
# 変更行のみに絞る（git diff の hunks だけ渡す）
git diff origin/main...HEAD -- src/auth/login.ts | head -200 | claude ...
```

### 2. ハルシネーション対策

LLM は「問題がある」と言いたがる傾向がある。**ファルスポジティブを前提にした運用設計**が必要。

- 出力をそのまま採用せず、エンジニアが最終確認するフローを維持
- 重大度 CRITICAL のみ CI でブロックし、HIGH 以下はコメントのみにする

### 3. プロンプトのバージョン管理

プロンプトファイルはコードと同じく Git で管理することを強く推奨する。

```
.
├── prompts/
│   ├── type-safety-review.txt
│   ├── security-review.txt
│   ├── perf-review.txt
│   ├── test-gen.txt
│   └── pr-description.txt
└── review.sh
```

プロンプトの変更が出力品質にどう影響するかを追跡できる。

## まとめ

| パターン | 主な用途 | 効果 |
|---|---|---|
| 型安全性チェック | TS の `any` / `as` 検出 | 型バグを PR 段階で除去 |
| セキュリティスキャン | OWASP Top 10 準拠 | ロジックバグ・インジェクション検出 |
| パフォーマンスレビュー | React 再レンダリング最適化 | 体感速度の改善 |
| テストコード生成 | 境界値テスト自動作成 | カバレッジの底上げ |
| PR Description 生成 | 変更影響範囲の文章化 | レビューコスト削減 |

Claude Code は「賢い Grep」として使うのが現時点での最適解だ。**LLM に最終判断を委ねるのではなく、人間のレビュアーが見落としやすいパターンを拾い上げる補助ツール**として位置づけることで、その真価を発揮する。

プロンプトの精度を上げることが、そのままレビュー品質の向上につながる。ぜひ自チームのコードベースに合わせてカスタマイズしてほしい。
