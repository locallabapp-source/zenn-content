## TL;DR

- Claude Code はコマンドラインから動作する Agentic AI コーディングツールで、単なるコード補完を超えたタスク実行が可能
- 「ざっくりした指示 → 自律実行」モデルを正しく活用すると、リファクタリング・テスト生成・ドキュメント整備が大幅に加速する
- 本記事では 3 週間の実用から得た 7 つのパターンを、良い例・悪い例のプロンプトと共に整理する

---

## はじめに

Claude Code（旧称 claude-engineer）は Anthropic が開発・提供するターミナル駆動の AI コーディングエージェントです。2025 年の GA 以降、Qiita や X（旧 Twitter）での実験報告が増えていますが「とりあえず動かしてみた」レベルの紹介が多く、**実務ワークフローへの組み込み方**を体系的にまとめた記事は少ない印象です。

本記事は 3 週間の実運用を経て「これは効く」「これは沼る」と感じたパターンを 7 つに整理したものです。チームへの導入検討や、既に使っているが伸び悩んでいる方の参考になれば幸いです。

---

## 前提: Claude Code の動作モデルを正しく理解する

Claude Code を使いこなす最大の前提は **「LLM ではなくエージェントとして扱う」** ことです。

通常のチャット LLM はターン制で動きます。

```
User → モデル → 出力 → ユーザーが次を入力
```

Claude Code はこうではなく:

```
User → サブタスク分解 → ファイル読み取り → コード生成 → テスト実行 → 修正ループ → 完了報告
```

という **ループ型の自律実行** を行います。つまり「指示の粒度」と「コンテキストの渡し方」が従来の LLM 活用とは根本的に異なります。

## パターン 1: CLAUDE.md で「作業の前提」を宣言する

### 概要

プロジェクトルートに `CLAUDE.md` を置くと、Claude Code はセッション開始時に自動で読み込みます。これを「チームへのオンボーディングドキュメント」と同じ感覚で書くと効果的です。

### 良い例

```markdown
# プロジェクト概要
Rust + axum の REST API。ドメイン層を src/domain/, インフラ層を src/infra/ に分離している。

# コーディング規約
- エラーは anyhow::Result で統一
- DB アクセスは必ず repository trait 経由
- 新規ファイルは必ず mod.rs に pub use で再エクスポート

# テスト方針
- ユニットテストは src/**/*.rs の末尾 #[cfg(test)] ブロックに書く
- 統合テストは tests/ 配下
- cargo test が通らない PR は merge しない

# 使ってよいコマンド
- cargo check, cargo test, cargo clippy
```

### 悪い例

```markdown
Rust のプロジェクトです。よろしくお願いします。
```

`CLAUDE.md` を書かずに使うと、エージェントがファイル構造を探索するだけで多くのトークンを消費します。ゴールとルールを事前宣言するだけで実行精度が体感 1.5 倍以上向上します。

## パターン 2: 「大きな指示 × 中間確認ポイント」の分割

### 概要

Claude Code は長い指示に対して「最初から最後まで一気に実行」しようとする傾向があります。大規模変更では途中で方向がずれることがあるため、**マイルストーンで止めるポイントを明示**すると安定します。

### 良い例

```
src/user.rs の UserService を以下の手順でリファクタしてください:
1. UserRepository trait を src/domain/repository.rs に抽出
2. ここで一旦止まって、私に差分を見せてください
3. OK を確認したら InMemoryUserRepository を src/infra/ に実装
4. 全テストが通ることを確認して完了報告
```

### 悪い例

```
UserService をきれいにしてください
```

曖昧な指示は「それなりの変更」を生成しますが、大量の想定外の差分が出て review コストが跳ね上がります。

## パターン 3: テスト先書きで精度を上げる

### 概要

「実装してください」より「まずテストを書いてください、それから実装してください」のほうが最終的な実装品質が高くなります。エージェントに TDD の思想を強制的に踏ませるアプローチです。

### プロンプト例

```
次の仕様を満たす parse_date 関数を実装してください:

仕様:
- "2025-01-15" 形式の文字列を受け取る
- (u16, u8, u8) = (year, month, day) を返す
- 不正な入力は Err を返す

手順:
1. まず tests/ に失敗するテストを書く
2. テストが失敗することを cargo test で確認する
3. 実装して全テストが通るまでループする
```

このパターンは特にユーティリティ関数・バリデーションロジックで強力です。エッジケースをテストで網羅させてから実装させると「正常系だけ通る実装」を防げます。

## パターン 4: 既存コードへのレビューコメントを一括対応させる

### 概要

PR レビューで付いたコメントを Claude Code に渡して一括対応させます。コメントのコピーと対象ファイルのパスを渡すだけです。

### プロンプト例

```
以下の PR レビューコメントをすべて対応してください:

ファイル: src/api/handler.rs
L45: unwrap() を使わず ? で伝播してください
L78: エラーメッセージを日本語にしてください
L90: この if-else は match に書き換えると Rustacean らしい

ファイル: src/domain/user.rs
L12: derive マクロに PartialEq を追加してください

対応後、cargo clippy でワーニングがないことを確認してください。
```

手動でやると 30 分かかる対応がほぼ自動化できます。コンフリクトが発生する変更でも、Claude Code はファイルを読んでから編集するため整合性が取れます。

## パターン 5: ドキュメント生成を「コードを読ませてから」やらせる

### 概要

「README を書いてください」だけでは汎用的なテンプレートが出てきます。**先にコードを読ませてからドキュメント生成**させると、実際の実装に即した内容になります。

### プロンプト例

```
以下の順番で README.md を生成してください:

1. src/ 配下の全 .rs ファイルを読んで、このプロジェクトが何をするツールか理解する
2. Cargo.toml の dependencies を読んで、主要ライブラリを把握する
3. 以下の構成で README.md を生成する:
   - # プロジェクト名
   - ## 概要 (2-3 文)
   - ## インストール
   - ## 使い方 (実際の関数/コマンド名を使う)
   - ## アーキテクチャ概要
   - ## ライセンス
```

「読んでから書く」を明示することが重要です。読まずに書くと嘘のコマンド例が生まれます。

## パターン 6: 「説明してから実装」で意図を揃える

### 概要

複雑な変更の場合、最初に「どう実装するか説明してください（まだコードは書かないで）」と指示し、方針合意してから実装させます。

### プロンプト例 (2 ターン構成)

**1 ターン目:**
```
src/infra/postgres.rs に接続プール管理を追加したいです。
deadpool-postgres を使う案と bb8 + tokio-postgres を使う案の
トレードオフを説明してください。コードはまだ書かないで構いません。
```

**2 ターン目 (説明を聞いた後):**
```
deadpool-postgres の案で進めてください。
先ほどの説明の通りの設計で実装してほしいです。
```

このパターンは「実装してみたら想定と全然違う」という手戻りを防ぎます。特にライブラリ選定が絡む場面で有効です。

## パターン 7: /compact で長いセッションを延命する

### 概要

長時間の作業セッションではコンテキストウィンドウが圧迫され、後半になるほど精度が下がることがあります。Claude Code の `/compact` コマンドは会話履歴を要約して圧縮し、コンテキストを延命します。

### 使いどころ

- 30 分を超えたセッション
- 大量のファイルを読み込んだ後
- エラーループが続いて会話が長くなった後

```
/compact
```

と入力するだけで会話が圧縮され、重要な文脈は保持されます。

### 注意点

`/compact` 後は、重要な制約（特定の実装方針・NG パターン）が薄れることがあります。その場合は `CLAUDE.md` を再読させるか、制約を再掲します。

```
/compact 後の確認: CLAUDE.md の規約を再確認してから作業を続けてください
```

## まとめ: 7 パターン一覧

| # | パターン | 効果 | 特に有効な場面 |
|---|---|---|---|
| 1 | CLAUDE.md 事前宣言 | 探索コスト削減・一貫性担保 | 新規プロジェクト開始時 |
| 2 | 中間確認ポイント明示 | 方向ずれ防止 | 大規模リファクタ |
| 3 | テスト先書き強制 | 実装品質向上 | ユーティリティ実装 |
| 4 | レビューコメント一括対応 | PR 対応時間の圧縮 | コードレビュー後 |
| 5 | 読んでからドキュメント生成 | 実態に即した文書 | OSS 公開前 |
| 6 | 説明してから実装 | 手戻り防止 | ライブラリ選定が絡む場面 |
| 7 | /compact で延命 | コンテキスト圧迫対策 | 長時間セッション |

## 付録: プロンプト設計の 3 原則

3 週間の実験から帰納した原則をまとめます。

**原則 1: ゴール・ルール・手順を分けて書く**

```
ゴール: ○○を実現する
ルール: △△は使わない、□□形式で統一
手順: 1. まず… 2. 次に… 3. 最後に…
```

この 3 点を明記するだけでアウトプットの再現性が上がります。

**原則 2: 「やること」より「やらないこと」を先に宣言する**

「既存の public API のシグネチャは変えないでください」「外部ライブラリの追加は Cargo.toml に明示してください」のように **NG 事項を先出し** すると、後から「あれ、ここ変わってる」という発見が減ります。

**原則 3: 成功条件を定量/定性で明示する**

「cargo test が全て pass すること」「clippy のワーニングが 0 件」「diff が 50 行以内」のように**完了条件を明示**すると、エージェントが自律的に検証ループを回してから完了報告するようになります。
